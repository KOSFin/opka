title: Scheduled automations
---

Orca automations run a prompt on a schedule from the CLI, so recurring triage, review, and maintenance tasks can start without you opening a worktree by hand. By the end of this page, you'll create a disabled automation, inspect it, and run it when you're ready.

## Create a safe first automation

Start with `--disabled` while you tune the prompt and target:

```bash
orca automations create \
  --name "Weekday triage" \
  --trigger weekdays \
  --time 09:00 \
  --prompt "Triage new issues and summarize blockers" \
  --provider codex \
  --repo my-repo \
  --disabled \
  --json
```

`--trigger` accepts presets such as `hourly`, `daily`, `weekdays`, and `weekly`, plus cron expressions or RRULE strings. Use `--timezone <tz>` when the schedule should follow a specific IANA timezone instead of the runtime default.

## Choose where runs happen

Use `--repo <selector>` when each run should create or select work in a repository. Use `--workspace <selector>` when the automation should run inside an existing Orca worktree instead:

```bash
orca automations create \
  --name "Nightly status" \
  --trigger "0 18 * * 1-5" \
  --prompt "Summarize today's changes" \
  --provider claude \
  --workspace active \
  --disabled
```

When you omit both target flags, Orca resolves the enclosing worktree from the current shell directory when it can.

## Precheck before a run

Skip scheduled work when a cheap shell probe fails (non-zero exit records a skipped run):

```bash
orca automations create \
  --name "PR review" \
  --trigger hourly \
  --precheck "gh pr list --json number -q .[0].number" \
  --prompt "Review requested PRs" \
  --provider codex \
  --repo my-repo \
  --disabled \
  --json
```

## Project host / setup targets

When the automation should run on a specific project host setup rather than only `--repo` / `--workspace`:

```bash
orca automations create \
  --name "Remote triage" \
  --trigger daily \
  --time 09:00 \
  --prompt "Triage open issues" \
  --provider claude \
  --project <projectId> \
  --host <host> \
  --disabled \
  --json
```

`--project` takes the project id or the display name from `orca project list`. `--host` takes `local`, `ssh:<target-id>`, `runtime:<environment-id>`, or the bare name from `orca host list`, and it can be omitted entirely when the project is set up on only one host — Orca uses that one. When the project is set up on several, the error names each host and the flag to select it.

Use `--project-host-setup <id>` when you already have a setup id. Optional `--source-context '<json>'` pins task/provider data to a host/account (pass `null` on edit to clear).

## Manage automations across hosts

The desktop **Automations** page loads schedules from this computer and supported connected Orca hosts into one table. The **Host** column shows where each automation is stored and scheduled; use **Filters → Host** to show one or more hosts, or return to **All hosts**.

When you create an automation in the desktop UI, **Create on** chooses its host before you choose a project. The project picker then shows projects available on that destination. Connected hosts that need a newer Orca server stay visible but disabled, with an **Update server** message, instead of disappearing from the picker.

## Missed-run grace

```bash
orca automations edit <automationId> --missed-run-grace-minutes 30 --json
```

## Reuse an existing automation session

For automations that target an existing worktree, add `--reuse-session` when later runs should continue in the previous live automation terminal instead of starting from a blank terminal each time:

```bash
orca automations create \
  --name "Inbox digest" \
  --trigger hourly \
  --prompt "Summarize unread mail" \
  --provider codex \
  --workspace active \
  --reuse-session \
  --disabled
```

Use `orca automations edit <automationId> --fresh-session --json` to switch the automation back to a fresh terminal per run.

## Extra agent arguments

Add arguments to the agent command for one automation, for example a different model:

```bash
orca automations create \
  --name "Docs pass" \
  --trigger daily \
  --prompt "Tidy the docs" \
  --provider claude \
  --extra-agent-args="--model opus --add-dir docs"
```

On each fresh run, Orca starts from the host's default Arguments for that agent and appends the extras. A model or effort option in the extras replaces the one in the defaults. Pass the value with `=` because it starts with `--`.

Saved extras use the same quoting on every host, including Windows: wrap values containing spaces in single or double quotes, and use single quotes to preserve backslashes in paths, such as `--add-dir 'C:\work\my docs'`. Orca passes these as literal arguments; shell commands and expansions are not supported.

Extras accept only model and effort options, plus Claude's `--add-dir`, for Claude, Codex, CodeBuddy, Cursor, Grok, and OMP. Permission, config, prompt, and session options are rejected. Extras require a fresh session for every run, so they can't be combined with `--reuse-session`. Use `orca automations edit <automationId> --extra-agent-args=` to clear them.

## Review and enable

List and inspect automations before enabling them:

```bash
orca automations list --json
orca automations show <automationId> --json
orca automations edit <automationId> --enabled --json
```

In the desktop automations list, use the search field to filter by **name**, **project**, or **prompt** text when you have many schedules.

Use **Filters** to narrow the list by **Host**, **Enabled** or **Paused** state, last-run outcome (**Failed**, **Succeeded**, or **Never ran**), or one or more **Agents**. Search inside the agent submenu when the list is long; active filters appear as removable pills above the table. The table shows the host, last-run result, and relative time for each automation. Click the **Name** or **Last run** column to sort; name sorts alphabetically, while last run defaults to newest first.

When the automation list is open, type in the search field and press **ArrowUp** or **ArrowDown** to move the selection through the visible matching rows. The list keeps the selected row in view; modified or composing input keeps its normal cursor behavior.

Use `edit` to change the name, prompt, provider, target, schedule, or enabled state. `remove` deletes an automation and its run history.

## Run on demand

After creating an automation, trigger it manually to check the prompt and target before waiting for the next scheduled time:

```bash
orca automations run <automationId> --json
orca automations runs --id <automationId> --json
```

If a run fails before it opens a workspace or reconnects to its target, open that run in Orca and click **Rerun** to queue a fresh manual run for the same automation.

## Scripts with an optional agent on Linux

The existing **Automations** list and editor also support **Script with optional agent**. Select **Create on** first, then a ready project folder on that execution host. The host must run Linux with a reachable, lingering systemd user manager and pass its durable process-scope probe. Unsupported hosts do not advertise command execution; reconnecting alone does not install those prerequisites.

Use the editor presets or a five-field cron expression for schedules. The RRULE parser supports its HOURLY/DAILY/WEEKLY subset with BYHOUR, BYMINUTE and weekly BYDAY; COUNT and second-level scheduling are not implemented. The scheduler polls once per minute.

Command automations must be enabled for **Run now** as well as scheduled execution. For a manual probe, keep the schedule safely in the future before enabling it.

Choose **Program**, **Shell script**, or **Python script** as the first step. **Never call an agent** with **No agent** runs entirely without a model. **Exit code 0 and changed JSON** continues only when the command exits successfully and its stdout is exactly a JSON object such as:

```json
{ "version": 1, "changed": true }
```

Return `changed: false` when there is nothing to review. Send diagnostic logs to stderr so stdout remains valid JSON. The optional agent stage currently supports **Codex, one turn** through the execution host's verified CLI, with an ephemeral session and read-only sandbox. Claude and continuing an existing agent conversation are not supported by this command pipeline. CLI availability and authentication must be configured on the execution host; this option does not establish automatic pool-account selection.

### Bound the monitoring command

For a small monitoring script, use **Program** with executable `/usr/bin/prlimit` and these **Arguments, one per line**, adapting the limits and script path to the job:

```text
--as=268435456
--cpu=15
--nproc=1024
--
/usr/bin/python3
/absolute/project/monitor.py
```

Also set the editor's **Timeout, seconds** to bound elapsed time. `prlimit` supplies inherited per-process address-space, CPU-time and process-count limits; these are not an aggregate cgroup memory budget or CPU quota for an arbitrary process tree. The product currently bounds command/lifecycle time and retained output, but does not configure per-run RAM, CPU-quota or cgroup PID budgets. Start with a small script that does not spawn worker trees.

### Keep reports available after restart

Use **History only** for the first monitoring schedule. Its output snapshot and run identity remain in **Runs** after a host restart. Final history retains the latest 100 runs per automation, with output limited to 16 KiB; it is not a permanent audit archive. Replaying the same manual request key is deduplicated within the retained 24-hour request window.

For long-term consultation, let the monitoring script maintain its existing daily files and index inside the project, and have the main agent read those files when asked. Opka does not create that file archive automatically. This mode needs no model call or external notification on each check.

**Primary chat report** requires a currently registered chat on the same execution host, folder and registration generation. The target also pins the runtime incarnation: after a host restart, reselect the chat before relying on delivery. Durable automatic delivery to that chat across restarts is not supported in this version; use history and project files for that requirement. A missing or stale required report target can refuse execution, so choose **History only** when unattended checks must continue independently of chat registration.
