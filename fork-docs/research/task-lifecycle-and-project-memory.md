# Полный цикл задач и долговременная память Opka

Дата: 2026-10-25. Статус: исследование и предложение к согласованию.

Память поможет продолжать работу между чатами и находить прежние решения. Она не заменяет привязку агента к карточке, очередь исполнения, проверку результата или управление доступом. Для Opka предпочтителен локальный проектный слой с коротким восстановлением контекста; автоматическое извлечение знаний стоит сравнить с ним на отдельном стенде перед включением по умолчанию.

## Что уже есть в Opka

Исходники: `7f785dc4ff5ca85ae5bc038773c1998ca22adae2`. Наличие механизма в коде не означает, что он автоматически подключён к каждому пользовательскому чату.

| Область | Реализация | Недостающая связь |
| --- | --- | --- |
| Документы задачи | task.md, notes.md, checkpoint.md, reports; SHA256 revision и регистрация источников | Отчёт и следующий шаг должны быть доступны из карточки без поиска по папкам |
| Состояние выполнения | project_task_items/attempts/events в существующей orchestration DB | Обычный чат не получает карточку в работу своей текущей сессией; launch требует coordinator Run |
| Восстановление | Ограниченный resume, последние попытки/события, checkpoint с явно непроверенной свежестью | Нужна гарантированная передача актуального пакета при каждом поддержанном входе |
| История разговоров | AI Vault, SQLite FTS5, индексирование изменений, проектная/хостовая область поиска, runtime RPC и CLI search | Архив реплик не выделяет действующие решения и не является автоматически памятью исполнителя |
| Сигналы агентов | Существующие hooks/status и orchestration lifecycle | Завершение turn/CLI не доказывает выполнение критериев; бизнес-результат требует отдельного события |

Особенно важно: session-search index является пересоздаваемым кэшем над transcript. В его схеме прямо предусмотрен сброс при смене версии. Единственную копию долговременных решений нельзя хранить в этом индексе. Он также хранит исходный текст без редактирования секретов: отправлять весь индекс внешнему memory provider нельзя.

Исходники для проверки: `src/main/project-tasks/task-workflow-schema.ts`, `task-context.ts`, `src/main/runtime/project-task-launch.ts`, `project-task-resume.ts`, `src/main/ai-vault-search/session-search-schema.ts`, `session-search-read-decision.ts`, `session-search-scope-catalog.ts`, `src/main/runtime/rpc/methods/ai-vault.ts`, `src/cli/handlers/search.ts`.

## Предлагаемый полный цикл

| Шаг пользователя | Действие системы | Что сохраняется |
| --- | --- | --- |
| Открыть проект или обычный чат | Определить зарегистрированный проект, execution host и текущую сессию; показать задачи без полного чтения архива | Стабильные идентификаторы, а не только basename/cwd |
| Попросить выполнить карточку | Найти точную задачу, уточнить неоднозначность, атомарно взять её текущей сессией | Попытка, revision, владелец и событие начала |
| Обсудить план | Восстановить относящиеся к задаче решения; подготовить соразмерный план | План и конкретное одобрение, если требуется; не approval на все внешние действия |
| Выполнить работу | Один агент работает сам; согласованные независимые части делегируются с ограниченным контекстом | Изменения, существенные решения, промежуточный checkpoint, ссылки на проверки |
| Получить сведения другого проекта | Запросить разрешённый контракт у его владельца; не подменять обмен прямым чтением исходников | Версия контракта, источник, ответ и зависимость |
| Приостановить или столкнуться с ошибкой | Зафиксировать препятствие и следующий шаг; отразить его на карточке | Последняя сохранённая точка и честное состояние связи |
| Передать результат на проверку | Проверить наличие результата, revision и актуальность свидетельств; независимый reviewer — по политике задачи | Отчёт, фактические команды/результаты, repository/base/head, замечания |
| Принять результат | Отделить вывод исполнителя от приёмки и внешних merge/deploy | Решение пользователя и итог; выбранные устойчивые знания для проекта |
| Вернуться позже другим чатом | Проверить исход прежней попытки и свежесть ссылок, загрузить короткое продолжение | Продолжение той же задачи без дублирующего исполнителя |

Карточка, чат и память связаны, но не тождественны. Карточка описывает результат, чат — способ взаимодействия с исполнителем, память — знания, полезные для следующих задач. Ветка/рабочая копия относится к исполнению. Координатор нужен составной работе, а не каждому небольшому исправлению.

## Какие виды памяти нужны

1. **Текущий контекст модели.** Временный: исчезает или сокращается, не является надёжным хранилищем.
2. **Checkpoint задачи.** Краткое состояние незавершённой работы: что сделано, что проверено, препятствие, следующий шаг. Связан с попыткой/revision, не заменяет план.
3. **Память проекта.** Принятые решения, причины, устойчивые ограничения, полезные находки. Для каждого знания нужны источник, дата, область действия и статус актуальности. Новое решение помечает прежнее как заменённое, а не стирает историю.
4. **Архив доказательств.** Transcript, activity, отчёты, diff, CI и документы. Сохраняется адресно и ищется по запросу; не вкладывается целиком в prompt.

Один и тот же факт не должен независимо редактироваться в пяти хранилищах. Авторитетный документ/запись имеет стабильный ID и revision; поисковый/векторный индекс — производная. Знание «обычно запускаем такую проверку» полезно; воспоминание «проверки прошли» не подтверждает новый head SHA.

## Сравнение готовых решений

Сравнение касается публичного кода и документации, не установленного поведения в Opka. Звёзды и активность проверены как признаки видимости проекта, но не считаются доказательством качества или безопасности. Заявления поставщиков о кратном сокращении токенов здесь не используются как результаты наших измерений.

| Решение | Механизм и зависимости | Поможет ли Opka |
| --- | --- | --- |
| [Engram](https://github.com/Gentleman-Programming/engram) | Go, SQLite + FTS5, MCP/HTTP/CLI. Значимые наблюдения сохраняет агент, поиск выдаёт краткие кандидаты с последующим чтением деталей. В core нет обязательного внешнего LLM/векторного сервиса для такого поиска. | Первый кандидат для ограниченного сравнения с собственным слоем. Нужно связать project/session identity с Opka, ограничить tool profile и проверить состав runtime/hook интеграции. Project assertion в его API прямо не является authentication/authorization. |
| [claude-mem](https://github.com/thedotmack/claude-mem) | Lifecycle hooks, worker service на Bun, SQLite, summaries и hybrid search с Chroma. Есть интеграции за пределами Claude Code, включая T3-managed providers; это не доказательство готовой поддержки Opka. | Полезны progressive search и автоматические observations. Полный observer требует оценки обработки данных, модельных расходов и фоновых компонентов. Установщик может менять hooks, зависимости и provider setup, поэтому не подходит как неявный побочный шаг. |
| [Mem0](https://github.com/mem0ai/mem0) | SDK и self-hosted/cloud варианты: извлечение и обновление memories, поиск через embeddings, настройка LLM/хранилищ. [OpenMemory](https://mem0.ai/openmemory) — отдельная MCP-facing продуктовая поверхность, а не гарантия одинаковых defaults с SDK. | Подходит, если нужен выделенный семантический memory backend. Самостоятельный deploy не гарантирует отсутствие внешних LLM/embedding запросов; маршруты и стоимость проверять отдельно. Не исправляет task lifecycle. |
| [Hindsight](https://github.com/vectorize-io/hindsight) | Retain/recall/reflect, banks, сервер с PostgreSQL в quickstart, модельная обработка и готовые coding-agent интеграции. Legacy Codex README уже не соответствует текущему дереву main — нельзя ставить по старому сниппету. |
| [Graphiti](https://github.com/getzep/graphiti) | Python, временной граф с происхождением фактов, graph DB, LLM и embedder; есть MCP server. | Полезен при сложных изменяющихся связях между сущностями. Для начальной памяти разработки добавляет инфраструктуру; tenancy/access control/ingestion остаются задачей приложения. Не выбран первым кандидатом. |
| [MCP memory reference server](https://github.com/modelcontextprotocol/servers/tree/main/src/memory) | Entities/relations/observations в JSONL. В просмотренном source searchNodes читает граф и ищет подстроки; read_graph возвращает всё. | Простой reference/prototype, но не готовая масштабируемая память наших проектов. Нужны дополнительная область доступа, управление актуальностью и bounded retrieval. Не подключать read_graph в каждый prompt. |
| [Letta](https://github.com/letta-ai/letta) | Stateful agent platform. Текущий README отправляет в letta-ai/letta-code; прежний V1 API server находится в archive. | Это скорее другой agent runtime, чем маленький memory plugin к Opka. Рассматривать как альтернативную платформу, не скрытую зависимость текущего плана. |

У Engram явно описано ограничение: формат хорошего знания поддерживается протоколом/агентом, а не автоматической гарантией качества записанного текста. Наличие БД не делает память достоверной. [Memory core](https://github.com/Gentleman-Programming/engram/blob/main/docs/codebase/memory-core.md).

У claude-mem полезен принцип «поиск → окружающие события → выбранные полные записи». Для нашей цели достаточно заимствовать этот способ выдачи, не включать весь observer по умолчанию. [Описание поиска](https://github.com/thedotmack/claude-mem#mcp-search-tools).

У Hindsight текущий [coding-agents package](https://github.com/vectorize-io/hindsight/tree/main/hindsight-integrations/coding-agents) имеет собственную фоновую обработку и autoUpdate. При встраивании в воспроизводимый релиз Opka версии должны фиксироваться нашей поставкой; пользовательские глобальные конфигурации не менять.

## Рекомендуемая архитектура Opka

Базовый слой должен работать без стороннего сервера: существующее состояние задач + checkpoint + принятые проектные решения + уже имеющийся поиск архива. Индекс пересоздаётся отдельно от долговременных данных. Перед добавлением нового persistence слоя проверить пригодность существующей durable runtime DB; не складывать уникальные знания в versioned cache.

Внешний memory provider подключать через небольшой адаптер поиска и сохранения. Агент видит проектные операции Opka, а не обязательный каталог всех административных tools поставщика. Opka выбирает scope из проверенной сессии и проекта, ограничивает результат, возвращает источники и ошибку провайдера. Недоступность дополнительного семантического поиска не должна мешать открыть карточку или прочитать её checkpoint; неизвестное состояние исполнения нельзя заменять локальной догадкой.

Предпочтительный пилот: native baseline против Engram. Добавить Hindsight только для сравнения автоматического извлечения/семантического восстановления, если это нужно по результатам baseline. Не устанавливать одновременно несколько observers, каждый из которых повторно импортирует весь transcript.

### Автоматика и качество знаний

- Runtime без вызова модели фиксирует идентификаторы, timestamps, revision, события запуска и принятые результаты; обновляет индекс изменённых документов.
- Агент сохраняет checkpoint и содержательные решения в ходе работы. Проверять обязательный checkpoint/result на границах передачи; аварийное завершение может оставить только последнюю сохранённую точку.
- Извлечение новых знаний делать из выбранного результата/решения в конце значимого этапа, с источником и бюджетом. Повторная обработка того же события не создаёт дубль. Не анализировать весь transcript заново после каждого turn.
- Автоматически извлечённое знание сначала является предложением. Изменение устойчивого правила, конфликтующие записи и межпроектный перенос требуют просматриваемого решения; автоматические события не требуют подтверждения каждого timestamp.
- Вспомненное содержимое — данные, не инструкция с повышенными правами. Оно не может само разрешить доступ к другому проекту, отключить проверки или вызвать внешний инструмент.

### Проекты и доступы

Идентификатор памяти — зарегистрированный project ID + owning host/namespace, не имя каталога. Worktree/вложенный repo могут наследовать память общего проекта; два одноимённых независимых проекта не объединяются. Перенос каталога требует явной привязки, а не новой случайной памяти.

Project filter, bank ID, group_id и topic_key не являются сами по себе границей безопасности. Если одному агенту запрещены данные другого проекта, ограничить также OS/filesystem authority и прямой доступ к memory backend/MCP. Общая память интеграции содержит явно разрешённые API-контракты и решения, не транскрипты и исходники соседнего проекта.

Сбор и внешний экспорт включаются явно для выбранного проекта. До отправки модели/embedding provider исключать запрещённые источники, минимизировать содержимое и проверять секреты; один regex или private tag не гарантирует отсутствия утечки. Не импортировать auth, production dumps и все пользовательские чаты по умолчанию. Удаление должно распространяться на производные индексы и внешние копии в рамках объявленной retention policy.

### Долговечность и работа с сервером

- Runtime хоста исполнения остаётся владельцем состояния задач. Закрытие Mac UI не уничтожает его записи, но продолжение серверных процессов после reboot требует проверенного service setup.
- Для общей памяти выбрать одного владельца записи и версионированный sync/export. Не открывать один SQLite файл одновременно с Mac и VM через сетевую папку и не делать автоматическое двустороннее слияние конфликтующих решений.
- Сохранять источники, revision, историю замены решений и идемпотентные receipt. Транзакция или очередь не должна терять записанный checkpoint при падении внешнего провайдера.
- Backup делать штатным согласованным SQLite backup/export, включая необходимые документы, не копией одного живого db-файла без WAL. Проверять восстановление после crash, migration и rollback; backup секретов не публиковать.
- Для старого SSH host без нового memory capability показать недоступность соответствующей функции. Потеря контакта — unverifiable, не exited; не передавать задачу второму исполнителю только по timeout памяти.
- Память не подтверждает актуальность файлов/контракта/CI: при продолжении сверять исходники и нужные SHA. Изменение approved revision и stale review обрабатываются существующими gates.

## Проверки перед выбором провайдера

На синтетических данных сравнить baseline и кандидатов по одинаковым сценариям, с фиксированными версиями/моделью и учётом всех расходов:

1. Обычный чат берёт карточку, сохраняет checkpoint/result; другой чат после restart продолжает без ручного пересказа.
2. Пять проектов с одинаковыми именами задач и конфликтующими соглашениями. Ни поиск, ни defaults записи не смешивают их; nested repos/worktrees сохраняют правильный общий scope.
3. Новое решение заменяет старое; вопрос «почему отказались» находит историю, а текущая инструкция использует только действующий вариант.
4. Два агента параллельно записывают разные знания; повторный запрос не дублирует запись; конфликт одного topic не решается молчаливым last writer wins.
5. Read-only/offline/older host, недоступный provider и падение во время записи дают явную ошибку и сохраняют прежние данные; никакого ложного Done.
6. Межпроектный запрос получает только разрешённый контракт. Прямое чтение закрытой памяти отвергается технически, если заявлена hard isolation. Имитация секрета и prompt injection не превращаются в глобальную инструкцию.
7. Месяц синтетической истории, backup/restore, смена пути/модели/embedding версии, удаление записи и переиндексация не теряют устойчивые решения и не восстанавливают удалённые факты из старого индекса.
8. 10/100/1000 фоновых карточек при одной активной: считать задержку старта/поиска p50/p95, размер БД, CPU/RAM, input/output tokens, embedding/ingestion/reflection calls и долю правильно восстановленных решений. Пустое ожидание не вызывает модель.
9. Русский запрос к английскому решению, перефразирование, короткий identifier и отрицательное знание «не использовать X». Это проверяет границы FTS и реальную пользу embeddings, а не только удачный поиск точного слова.
10. Полная стоимость включает создание памяти, повторные попытки и consolidation, а не только сокращение prompt исполнителя. Отдельно считать устаревшие/ложные воспоминания и число пользовательских исправлений.

Бюджеты bootstrap/resume из [плана выполнения](../plans/card-to-result-workflow.md) остаются проектными целями. Общий prompt считать по фактическим instructions + schemas + task packet + memory results. Ни экономия токенов, ни задержки конкретного плагина этим исследованием не измерены.

## Выполненная проверка

Прямым запуском установленного Vitest с ORCA_BACKGROUND_LAUNCH=1 пройдены 4 файла и 19 тестов: task-five-projects, task-workflow-store, session-search-store-scope-catalog, session-search-fts5-contract. Это unit/integration проверки хранения и индекса, не прогон пяти настоящих агентов, SSH deployment или оценка стороннего memory backend.

Первый штатный pnpm test остановился до тестов: локальный pnpm попытался выполнить install, который отказал на no-TTY purge guard. CI/force и переустановка зависимостей не использовались; прямой Vitest использовал имеющееся дерево зависимостей. Product source и lockfiles не изменены.

Marketplace search по Mem0/Zep/memory не нашёл подходящую готовую интеграцию среди возвращённых результатов; это не утверждение об отсутствии таких расширений вообще. GitHub-кандидаты изучались непосредственно. Скилл-инструкция не создаёт постоянное хранилище сам по себе.

Следующий согласуемый срез: исправить CLI/update дефекты, завершить единый chat→card→report lifecycle, добавить минимальный проектный memory contract и провести сравнение baseline/Engram на изолированных профилях. Включение облака, автоматического transcript ingestion, новых services и настоящих model runs требует отдельного выбора доступа/бюджета. Установленные приложения и серверы этим исследованием не менялись.
