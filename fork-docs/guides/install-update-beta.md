# Установка и обновление Opka beta

Это отдельный экспериментальный форк, не обновление рабочей Orca. Текущий подтверждённый статус сборок, выпуска и установки — в [журнале итерации 5](../iterations/005-installers-and-updates.md). Наличие инструкции не означает, что релиз уже опубликован или установка проверена.

## Какие файлы нужны

Только [Releases KOSFin/opka](https://github.com/KOSFin/opka/releases):

- Mac с Apple Silicon: `opka-macos-arm64.dmg`.
- Linux x64: `opka-server-linux-x64.tar.gz` для самостоятельного запуска. Обычное SSH-подключение из приложения использует встроенную управляемую установку runtime; вручную распаковывать архив для него не требуется.
- `SHA256SUMS` и `opka-*-provenance.json`: целостность файлов, версия и исходный коммит.

Intel Mac, Android и Windows installers не входят в эту beta. CI проверяет дополнительные платформы для совместимости серверных компонентов; это не обещание готовых установщиков для них.

## Mac: первая установка

1. Скачайте DMG и `SHA256SUMS` одного и того же выпуска. Проверьте SHA-256 DMG против его строки в checksums; на Mac команда `shasum -a 256 opka-macos-arm64.dmg` только читает файл.
2. Откройте DMG и скопируйте **Opka.app**, не Orca.app, в Applications. Не заменяйте рабочую Orca. Не запускайте приложение из нескольких копий DMG одновременно.
3. Эта beta не подписана Developer ID и не notarized. Если macOS блокирует открытие, используйте штатное подтверждение macOS только после проверки источника. Не отключайте Gatekeeper и не выполняйте команды снятия quarantine.
4. В Opka добавьте тестовую папку проекта или новый тестовый SSH-хост. Рабочие проекты и аккаунты не переносятся автоматически.

У Opka собственные bundle ID `io.github.kosfin.opka`, протокол `opka:` и профиль `~/Library/Application Support/Opka`. Installation-home файлы находятся в `~/.opka`; управляемые remote binaries — в `~/.opka-remote`. Имена `.orca/project.yaml` внутри проектов сохраняются ради совместимости файлов задач.

CLI регистрируется в приватном каталоге профиля командой `opka`; глобальная `orca` не заменяется. Settings → CLI показывает точный путь. Для вызова из внешнего shell используйте этот полный путь либо добавьте показанный каталог в PATH самостоятельно. Авторизация Codex/Claude — отдельная настройка, не часть установки приложения. Автоматическая перезапись user-global hooks отключена; собственные account/runtime homes и OpenCode profile overlays обслуживаются отдельно.

## Mac: обновление

1. Opka проверяет собственный feed и показывает доступный выпуск.
2. **Download installer** скачивает DMG и проверяет checksum. Повреждённый файл не предлагается открыть.
3. **Open installer** повторно проверяет файл и открывает DMG; эта кнопка не завершает приложение и не заменяет его самостоятельно.
4. Закончите активные операции и закройте только Opka. Подтвердите замену Opka.app в Applications. Рабочую Orca не закрывайте и не заменяйте.
5. Запустите Opka, проверьте версию в Settings, проекты и SSH-подключение.

Профиль находится вне app bundle и при обычной замене не удаляется. Сохранение всех PTY и privacy grants между unsigned beta builds ещё требует проверки; не рассчитывайте на бесшовное продолжение активного терминала до соответствующего результата в журнале.

## Новый сервер

Рекомендуемый сценарий — добавить **новый тестовый сервер** в Opka по SSH. Приложение использует существующий versioned deploy/activation механизм и собственный remote namespace. Номер desktop beta и content-hash серверного slot — разные идентификаторы; соответствие подтверждается исходным коммитом и manifest, а не совпадением строк версии.

Самостоятельный архив не устанавливает systemd/launchd service, не открывает firewall и не меняет глобальный PATH. Распакуйте его в новый отдельный каталог конкретной версии; `./opka-server --help` показывает параметры. Первый пробный запуск можно выполнить с `--bind 127.0.0.1 --port 0 --no-pairing`, задав отдельный абсолютный `ORCA_USER_DATA`. Завершайте только этот процесс. Не публикуйте pairing/readiness вывод в чат или репозиторий.

Для постоянной службы, собственного порта и удалённого доступа сначала определите владельца процесса и каталога данных. Нельзя указывать профиль рабочей Orca или существующего runtime. Прямой доступ из интернета не требуется: используйте SSH forwarding и loopback.

## Откат

Перед первым переходом A→B сохраните предыдущий DMG и резервную копию **закрытого профиля Opka**. В профиле могут быть секреты: backup должен оставаться приватным, с сохранёнными правами, не попадать в git/Actions artifacts.

Если B не запускается, закройте только Opka и верните предыдущую Opka.app из проверенного выпуска. Старый binary не гарантирует чтение схемы данных, обновлённой B: при необходимости восстанавливается соответствующая резервная копия профиля, а не произвольная смесь отдельных файлов.

У самостоятельно запущенного сервера сохраняйте отдельные каталоги A и B, используйте один профиль только одним процессом. Откат binary и откат данных — разные действия. Управляемый SSH runtime использует штатный activation/rollback механизм; не удаляйте чужие slots, locks или snapshots вручную.

## Что считается готовым выпуском

Успешный полный `pr.yml:verify` на точном коммите, реальные DMG/ZIP/server archive с проверенными provenance/checksums, опубликованный immutable tag, затем отдельно зафиксированные install/reconnect/update A→B/rollback проверки. Зелёные unit-тесты или кнопка в GUI сами по себе этого не доказывают.
