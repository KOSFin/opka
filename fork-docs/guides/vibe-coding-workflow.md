# Работа от задачи, а не от ветки

## Обычный день

1. Откройте **Tasks** и выберите свой проект. **All projects** — общий обзор, а не ещё один проект. Одна карточка описывает нужный результат, даже если изменение затронет backend, web и worker сразу.
2. **New task**: название и необязательное описание. Например: «Исправить вход после истечения сессии», «Не менять права пользователей; проверить web и backend». Выбирать репозиторий, ветку, агента и модель при записи идеи не нужно.
3. Откройте карточку. В **Plan** — план; **Edit plan** позволяет изменить Markdown-документ; **Activity** содержит историю и управляемые попытки. Панель закрывается, доска не делится постоянно пополам. Несохранённые изменения требуют отдельного решения при закрытии.
4. Для обсуждения нажмите **Plan with agent** и выберите агента через привычный launcher Orca. Он готовит **черновик**, который вы просматриваете и отправляете сами; беседа не становится managed attempt. Кнопка доступна, когда интерфейс знает рабочую копию и её owning host. Иначе скопируйте **More actions → Copy resume context** в карточке и вставьте контекст в нужный чат.
5. Уточните критерии и план с агентом. План сохраняйте в документ задачи, длинные находки — в соседний `notes.md`, следующий шаг перед сменой чата/аккаунта — в `checkpoint.md`. Не требуется переносить весь прошлый диалог в новый.
6. Пока у карточки нет managed attempts, двигайте её между Planned / In progress / Review вручную — например, если работаете сами или с обычным агентом. **Done** требует записать результат и проверки. Это ваше решение, а не заявление программы, что CI/production проверены. Те же действия доступны клавиатурой через **Task status** внутри карточки.
7. Для supervised worker: **Approve plan**, затем существующий координатор запускает задачу через `orca project-task start` или форму **Start managed worker** в **Activity**. Код выполняется в выбранной рабочей копии; она должна принадлежать этому проекту и хосту. Пустой `repos: []` означает все зарегистрированные репозитории проекта, не весь сервер. Существующие явные ограничения сохраняются.
8. Managed attempt сам меняет фазу по достоверным runtime-событиям. Его карточку нельзя вручную перетащить в Done, скрыв незавершённую или непроверенную работу. Результат → независимое ревью → исправления при необходимости → решение о принятии. Merge/deploy требуют своих проверок и разрешений.
9. Завершённые задачи можно оставить в Done или отправить в **More actions → Archive**. **View & filters → Include archived** возвращает доступ к ним. Архив не удаляет план, заметки, чаты, ветки и историю.

## Большая задача

Карточка родительской задачи хранит итоговую цель и критерии. Подзадачи полезны там, где есть независимый проверяемый результат, а не на каждую команду агента. Они могут относиться ко всему проекту. Ветки/рабочие копии — детали исполнения, не ещё один список бизнес-задач. Завершение родителя заблокировано, пока текущие подзадачи/зависимости не приняты.

Координатору можно дать задачу составить декомпозицию и создать эти документы; это не механически enforced роль. Программа пока не раздаёт весь backlog агентам автоматически, не гарантирует соблюдение инструкции одним промптом и не сливает ветки сама. Не держите десятки несвязанных задач в одном чате: карточка и checkpoint — точка возобновления конкретной работы.

## Что где находится

- **Tasks** — планы и результаты. Доска по умолчанию; list/tree и необязательные repo/source фильтры находятся в **View & filters**.
- **Working copies** — техническая доска Git checkouts. `main` там — ветка, не задача. Её не нужно открывать для обычного планирования.
- **External trackers** — существующие внешние интеграции; корпоративные карточки не создаются автоматически на каждую внутреннюю подзадачу.
- `task.md`, `notes.md`, `checkpoint.md` — обычные файлы зарегистрированного проекта. Фактические пути доступны в **How tasks work · file locations**. Runtime хранит подтверждения и попытки отдельно; редактирование Markdown не подделывает их.

При возврате доска показывает последний ограниченный по памяти снимок и проверяет владельца данных. Ошибка связи видна явно; старые карточки не выдаются за проверенные текущие данные. Отдельный проект получает live updates, общий обзор проверяется при открытии/Refresh. Локальный и удалённый учебные проекты независимы: одинаковое название задачи не означает синхронизацию файлов.

Для нового аккаунта откройте тот же проект и используйте сохранённый checkpoint/Copy resume context. Авторизация аккаунтов и лимиты не хранятся в файлах задачи.
