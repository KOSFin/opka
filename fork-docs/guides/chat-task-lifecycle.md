# Задача из обычного чата

Статус: исходники итерации 6. Эти изменения ещё не опубликованы в установщике; установленная rc.1 их не получает до выпуска и обновления. Проверки и ограничения — в [журнале](../iterations/006-chat-task-lifecycle.md).

## Как пользоваться

1. В **Tasks** выберите проект, создайте карточку с целью и критериями результата. Утвердите текущий план через **Approve plan**.
2. В обычном чате этого проекта скажите «Выполни задачу …». Либо выберите **Work on task** в карточке и агента. При неоднозначном названии агент должен уточнить карточку, а не выбирать случайную.
3. Агент берёт карточку своей сессией. Она становится **In progress**. Содержательные этапы и препятствия сохраняет через task CLI; runtime записывает системные события. Ошибка или окончание ответа не означает готовность задачи.
4. Результат с фактически выполненными проверками отправляется в **Review**. В карточке откройте **Reports & notes**: там отчёт, checkpoint и заметки, а также их точные пути в проекте. Полный отчёт не загружается в каждое сообщение автоматически.
5. После проверки примите результат или верните на доработку. Только отдельная приёмка делает **Done**. Это не автоматический merge/deploy и не доказательство прохождения внешнего CI.

Новый проект получает короткие project-scoped skills при **Set up task files**. Для уже настроенного проекта используйте **More actions → Enable agent task workflow**. Затем начните новый чат, чтобы агент обнаружил skill. Пользовательские `AGENTS.md` и глобальные skills не переписываются; конфликтующий custom skill сохраняется, действие выдаёт ошибку.

## Продолжение в другом чате

Пока задача занята, другой чат не может автоматически перехватить её. Владелец прекращает правки, сохраняет handoff checkpoint и явно освобождает попытку. Новый чат читает resume и берёт новую попытку. Освобождение не закрывает чат/терминал и не доказывает остановку процесса. Не запускайте продолжение до фактического прекращения старой работы.

Если старый владелец недоступен, автоматического перехвата по таймеру нет. Проверка и подтверждённая передача недоступной сессии остаются отдельным следующим срезом; не снимайте блокировку редактированием БД. Изменённый план требует нового approval, даже если старая попытка освобождена.

## Что делает CLI

Команды запускаются **внутри Opka** её собственным executable из `ORCA_CLI_COMMAND`, с унаследованным `ORCA_USER_DATA_PATH`. Это не глобальная `orca` и не другая установленная Orca. Внешний непривязанный Codex/Claude не получает identity только из названия папки.

- `project-task board` / `resume --id …` — найти карточку и прочитать ограниченный контекст.
- `claim --id … --revision …` — взять утверждённую карточку в текущем чате без нового worker.
- `progress --id … --revision … --attempt … --checkpoint … [--blocker …]` — сохранить этап/препятствие.
- `progress … --release` — сохранить checkpoint и освободить собственную попытку для продолжения.
- `complete … --checkpoint … --file report.md` — сохранить результат и запросить Review, не Done.
- `documents --id … [--path …]` — список документов одной задачи или чтение выбранного документа.

Runtime сам определяет `checkpoint.md`, `activity.md` и `reports/<attempt-id>.md` рядом с `task.md`. Повторная отправка того же результата не дублирует его; другой результат не перезаписывает уже поданный отчёт. Ошибка хранения оставляет задачу незавершённой и записывает blocker. Документы — данные проекта, не новые разрешения агенту.

На SSH-хосте действует runtime этого хоста. Старый сервер без новых методов должен вернуть явную ошибку совместимости; локального fallback к чужим файлам нет. Автоматический scheduler, независимый AI-reviewer и Engram в этот срез не включены.
