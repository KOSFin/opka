# Из карточки в проверенный результат

Статус: предложение после аудита исходников 2026-10-22. Пользователь запросил план; автоматический конвейер ещё не реализован и не объявляется работающим. UI-исправления навигации/Source Control ведутся отдельно в [текущем журнале](../iterations/004-publication-and-ci.md).

## Пользовательский сценарий

1. Пользователь создаёт карточку в общем проекте: цель, контекст, ограничения, критерий готовности. Выбирать репозиторий заранее необязательно. Хост определяется проектом, а не открытым терминалом.
2. **Составить план** запускает planner с ограниченным resume-пакетом именно этой карточки. Он исследует код, сохраняет план и риски в task.md, решения — в notes.md. Не получает все документы и MCP проекта в каждый prompt.
3. В карточке появляется итог планирования: что будет изменено, в каких репозиториях, какие проверки и внешние операции нужны. Пользователь корректирует план или нажимает **Одобрить и выполнить**. Одобряется конкретная revision, не «любой будущий текст».
4. Runtime создаёт/восстанавливает coordinator Run и изолированные рабочие копии для выбранных исполнителей. От пользователя не требуются terminal handle, Run ID и внутренний placement JSON. Второй клик не создаёт вторую попытку.
5. Координатор ведёт зависимости и результат, исполнители выполняют небольшие связанные части. Карточка показывает этап, хост, активных агентов, блокер, последнюю запись и **Открыть агента / Приостановить запуск новых работ / Остановить**. Репозитории и ветки — детали исполнения, а не отдельные карточки вместо бизнес-задачи.
6. Перед передачей следующему исполнителю формируется короткий packet: актуальная задача/revision, цель подзадачи, допустимые репозитории/пути, входные SHA, решения и критерий приёмки. Системные события записывает runtime; содержательные решения/проверки — агент в notes/report/checkpoint. Не писать тысячи одинаковых строк в task.md.
7. После отчёта исполнителя запускается отдельный reviewer: другой attempt/agent, зафиксированные base/head SHA, критерии плана, результаты проверок и diff. Его текст — вывод модели, не автоматически подтверждённый CI. Замечания возвращаются исполнителю, затем ревью повторяется по новым SHA.
8. Для нескольких репозиториев отдельный integration этап проверяет согласованный набор изменений: API-контракт, версии, pipeline и интеграционные тесты. Один удачный unit test или MR одного репозитория не делает всю карточку готовой.
9. В карточке показывается результат: изменённые репозитории и SHA, реально выполненные проверки, вывод reviewer, оставшиеся ограничения, документы, ссылки MR. Пользователь принимает результат или возвращает замечания. Merge/deploy/запись в Kaiten требуют отдельной политики и разрешений; одобрение плана их не подразумевает.
10. Архив сохраняет историю, документы и ссылки. Автоматически не удаляет чаты/worktrees. Удаление слитых копий — отдельное recoverable действие после проверки чистоты, merge state и отсутствия активных агентов.

Кнопка в карточке должна показывать следующее допустимое действие: **Составить план → Одобрить и выполнить → Открыть выполнение → Проверить результат → Принять / Вернуть**. Не показывать одновременно десяток внутренних RPC-команд.

## Что должна гарантировать программа, а не обещание в prompt

- Владелец выполнения — runtime хоста, не открытое окно Mac. Закрытие UI не отменяет уже принятый запуск. Перезапуск VM требует отдельно настроенного штатного сервиса; нынешний учебный стенд такой гарантии ещё не даёт.
- Каждая стадия связана с task ID, approved revision, Run и Dispatch. Отчёт без этих связей не переводит следующую стадию. Команда повторяется с idempotency key, события — с receipt/cursor. Хранение расширяется в существующей orchestration DB, не второй очереди в Markdown.
- Новый этап запускается по подтверждённому событию и проверенным prerequisites, а не по разбору фразы «готово» на экране терминала. Отчёт не равен приёмке; idle/exit/native child hook не равны завершению бизнес-задачи.
- Потеря связи означает **unverifiable**. Нельзя запускать замену исполнителю, пока не выяснен исход прежнего Dispatch. Используется существующий lifecycle/status store; новый status store для карточек не нужен.
- Перед передачей/завершением стадии проверяется наличие обязательного checkpoint/report и его соответствие revision/SHA. Если агент забыл документ, runtime запрашивает исправление или останавливается с понятным блокером. Он не придумывает журнал задним числом.
- Изменённый план не наследует старое approval. Продолжение другой revision возвращает gate пользователю. Проверки и ревью устаревают после изменения соответствующего head SHA.
- Смена аккаунта — новый provider launch с сохранённым task packet и проверкой прежней попытки, а не копирование access tokens/transcript. Не обещать перенос CLI-сессии между провайдерами, если это не поддерживает их адаптер.
- Дефолты agent/model/effort берутся из настроек пользователя. Профили planner/code/review могут их переопределять; недоступная модель даёт понятную ошибку. Параллелизм регулируется бюджетом/зависимостями, не произвольным глобальным «один worker». Бездействующий координатор ждёт события, не держит дорогой polling LLM-цикл.
- Instructions/MCP выдаются по роли и задаче; сторонние документы считаются данными. Строгий запрет координатору писать код требует capability/tool policy в launch adapter, а не строки в AGENTS.md. Такой enforcement нельзя обещать до отдельной проверки адаптеров.
- Kaiten получает одну понятную командную карточку/результат на значимую задачу, не каждую внутреннюю подзадачу. GitLab MR и CI привязываются к конкретному repository/head; статус «проверено» требует проверки именно этого head. Провайдеры подключаются через уже имеющиеся интеграции и их approvals.

## Этапы реализации после одобрения

### A. Один полный проход из карточки

- Связать planner-диалог с карточкой/attempt и автоматически прикладывать task packet при запуске/продолжении.
- Добавить host-owned start-or-resume coordinator без ручных handles, используя текущие Run/worker-start и revision guards. Проверить дополнительные capabilities у старых peers; не создавать локальный fallback вместо сервера.
- Заменить техническую форму в основном UI на выбор профиля агента и **Одобрить и выполнить**. Диагностику Run/Dispatch оставить в details.
- Реализовать обязательный checkpoint/report gate и видимый блокер при его нарушении.
- Сначала один repository и один managed attempt; не внедрять массовый scheduler одновременно с этим срезом.

Приёмка: реальная карточка→план→approval→изолированный worker→report→ручное решение на Mac и учебном SSH host. Двойной клик, редактирование approved plan и закрытие UI не порождают дублей и не теряют связь с попыткой. Для harness используется детерминированный протокольный агент; настоящая модель проверяется отдельно с согласованным аккаунтом/бюджетом.

### B. Независимое ревью и возврат замечаний

- Добавить тип стадии и доказательства SHA в существующие attempts/events с additive migration.
- По валидному implementation report запускать reviewer; его identity отделена от implementer.
- Ввести цикл findings→исправление→повторное ревью без повторного пересказа задачи пользователем. Условия остановки: лимит согласованных затрат/попыток, недостающая authority, неустранимый блокер — показать пользователю, не крутиться бесконечно.
- На карточке различать «агент считает готовым», «проверки выполнены» и «пользователь принял».

Приёмка: reviewer отвергает первую попытку, следующая исправляет замечание, изменение head делает прежнее ревью устаревшим, чужая revision/report не проходит gate. Отсутствующий report не запускает reviewer.

### C. Несколько репозиториев и итоговая интеграция

- Несколько подзадач/исполнителей работают в независимых копиях со стабильными repo/base/head ссылками.
- Integration attempt получает набор результатов, готовит согласованную проверку и MR-предложение. Не «сливать пять веток» без учёта разных Git-репозиториев.
- Сохранить независимое одобрение внешних записей и merge/deploy. Ветка координатора не обязана быть общей целью всех изменений.
- Отдельно предложить cleanup принятых рабочих копий с recoverable snapshot и проверкой реального состояния Git/процессов.

Приёмка: frontend+backend изменение с двумя MR, интеграционная ошибка на первой сборке, исправление, точные новые SHA и CI, возврат к карточке из нового чата/аккаунта по checkpoint. Никакого production deploy в QA.

### D. Несколько проектов и фоновые очереди

- Только после A–C добавить event-driven очередь разрешённых карточек и ограничения ресурсов/приоритеты; использовать существующие автоматики/Run lifecycle, не cron, который каждый раз шлёт всю историю всем агентам.
- UI даёт обзор пяти проектов: что выполняется, ждёт ревью/решения, где потерян контакт; переход открывает конкретную карточку и её агента.
- Секреты, аккаунты, глобальные полномочия, native-child наблюдения не наследуются молча от другого проекта.

Приёмка: пять синтетических проектов с несколькими одновременно работающими PTY, отключение/возврат клиента, перезапуск runtime, duplicate events, один offline host, смена аккаунта на завершённой попытке. Проверять отсутствие дублей, контекстных утечек и ложного done, а не число созданных коммитов.

## Рекомендуемая ближайшая граница

Сначала закрыть текущие UX-регрессии и принять их вручную. Затем одобрить **этап A** как один вертикальный срез. B–D — полный план направления, не обещание включить всё одним большим патчем. Для первого настоящего model-driven прохода отдельно согласовать провайдера/модель, доступы, тестовый проект и бюджет; до этого никаких реальных токенов/корпоративного кода в учебном профиле.
