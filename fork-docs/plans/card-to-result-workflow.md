# Из карточки в проверенный результат

Статус: предложение после аудита исходников 2026-10-22, уточнено 2026-10-25 после пользовательского теста и исследования OpenClaw Workboard. В исходниках итерации 6 реализован срез обычный чат → claim/progress/report → ручной Review, но полный автоматический конвейер ещё не объявляется работающим. Текущие результаты и границы — в [журнале](../iterations/006-chat-task-lifecycle.md). Изменение этого плана не является апрувом реализации всех последующих срезов или запуска моделей.

## Уточнение: обычный чат — полноценный вход

Пользователь не обязан запускать агента специальной кнопкой карточки. Обычный чат внутри подключённого проекта, кнопка карточки и делегирование должны использовать один механизм привязки исполнения. Прежний вариант с обязательным coordinator Run для каждой задачи слишком тяжёл для этого сценария; ниже координатор остаётся опцией для действительно составной работы.

1. Пользователь пишет в уже открытом чате: «Выполни задачу X». Агент получает краткий список совпадений только текущего проекта; при неоднозначности уточняет выбор. Чат без ссылки на задачу не должен молча создавать карточку или присваивать ближайшую по названию.
2. Агент берёт выбранную карточку в текущей сессии. Runtime атомарно связывает task/revision/host/session/attempt и возвращает ограниченный пакет продолжения. Повторный запрос не дублирует попытку. Чужая активная или unverifiable попытка запрещает автоматический перехват; истечение таймера само по себе не доказывает exited.
3. Планирование и исполнение различаются: план можно готовить до одобрения, изменение кода требует действительного разрешения на соответствующую revision. Привязка сессии не означает согласия на merge/deploy или другие внешние действия.
4. Runtime фиксирует начало, связь с агентом и системные события. Агент сохраняет содержательные решения, следующий шаг и результат; их пути возвращает операция карточки, а не придумывает агент. Отчёт виден в карточке. Завершение turn/CLI не делает Done: без обязательного результата показывается препятствие, с результатом — ожидание проверки/приёмки.
5. Другой чат продолжает работу по той же карточке после проверки прежнего владельца, читая короткий checkpoint и нужные документы, а не всю переписку. Кнопка карточки лишь удобный способ открыть этот же сценарий.

Произвольный внешний CLI без подключения к Opka не может гарантированно обновлять доску. Требуется обнаруживаемая проектная интеграция с привязанными к собственной установке CLI/profile и session identity. Она не должна подменять глобальную команду рабочей Orca или молча переписывать пользовательский AGENTS.md. Текстовые инструкции помогают агенту выбрать действие; корректность записей и отсутствие дублей обеспечивает runtime, а не обещание модели.

## Что заимствуем из OpenClaw, а что не переносим

Read-only исследование официальных [Workboard docs](https://docs.openclaw.ai/plugins/workboard), [agent tools source](https://github.com/openclaw/openclaw/blob/main/extensions/workboard/src/tools.ts) и [memory overview](https://docs.openclaw.ai/concepts/memory), 2026-10-25. OpenClaw локально не устанавливался и не запускался.

- Заимствуем принципы: связь существующей сессии с карточкой; явное получение владения; ограниченное чтение одной карточки; runtime-owned lifecycle; результат, проверки и вложения; изменения по событиям, а не постоянная полная перезагрузка доски.
- Не переносим весь Gateway, отдельную БД/очередь, полный каталог Workboard tools, обязательного Board agent, вторую доску сессий в основном пользовательском сценарии или их ограничения параллелизма по owner/agent. В Opka уже есть task store, attempts/events, host routing и Markdown-документы — расширяем их.
- Не копируем автоматическое приравнивание завершения сессии к готовому результату. Документация OpenClaw отдельно предупреждает: worker-reported proof не является независимой проверкой. Приёмка остаётся отдельным решением.
- Детальные журналы хранить и читать по запросу; краткие устойчивые решения отделять от ленты событий. Файловое хранение само по себе не уменьшает контекст — важно, что именно адаптер действительно отправляет модели.

## Минимум служебного контекста

Сравнение готовых memory backend, существующего поиска Opka, долговечности и сценариев приёмки: [полный цикл задач и долговременная память](../research/task-lifecycle-and-project-memory.md). Подключение провайдера не заменяет реализацию этого lifecycle; сначала baseline и изолированный пилот, не автоматическая установка всех найденных плагинов.

- Базовая инструкция сообщает о доступных задачах и способе взять/продолжить конкретную карточку. Полный orchestration guide и схемы всех административных инструментов не выдаются каждому исполнителю заранее. Обнаружение операций зависит от возможностей адаптера; огромный универсальный tool с огромной схемой не считается оптимизацией.
- Базовые действия исполнителя: найти/открыть, взять/продолжить, сохранить checkpoint, передать результат или блокер. Разбиение, управление очередью и межагентные сообщения загружаются только когда нужны. Это роли операций, не уже реализованные имена API.
- Пакет задачи содержит цель, действующие ограничения, критерии готовности, текущий шаг, существенные решения и ссылки. Полные отчёты, исходники и история остальных карточек доступны адресно, не вкладываются автоматически. Нельзя молча обрезать существенные требования ради бюджета: выдавать признак усечения и требуемое чтение.
- Проектные устойчивые решения, checkpoint задачи, append-only activity и отчёт имеют разные роли. Предложения в долговременную память должны быть просматриваемыми, с источником и областью проекта; не копировать туда каждую реплику, секреты или сведения другого проекта. Этот план не создаёт .codex/memory и не меняет глобальную память.
- Целевые бюджеты для будущих измерений: до 400 токенов постоянной служебной инструкции и около 1–2 тысяч токенов стандартного resume без большого плана. Это проектные ориентиры, не измеренные результаты и не лимит на необходимый контекст задачи. Считать фактическую сериализацию инструкций, tool schemas и результатов для адаптера/модели, не оценку символы/4.
- При 10/100/1000 фоновых карточках неизменённый пакет активной задачи не должен расти. Сравнивать токены, RPC/LLM-вызовы и задержку отдельно. Ожидание зависимости и простое обновление карточек не вызывают модель; семантическая обработка результата может требовать отдельного turn и учитывается в бюджете.

## Пользовательский сценарий

1. Пользователь создаёт карточку в общем проекте: цель, контекст, ограничения, критерий готовности. Выбирать репозиторий заранее необязательно. Хост определяется проектом, а не открытым терминалом.
2. **Составить план** запускает planner с ограниченным resume-пакетом именно этой карточки. Он исследует код, сохраняет план и риски в task.md, решения — в notes.md. Не получает все документы и MCP проекта в каждый prompt.
3. В карточке появляется итог планирования: что будет изменено, в каких репозиториях, какие проверки и внешние операции нужны. Пользователь корректирует план или нажимает **Одобрить и выполнить**. Одобряется конкретная revision, не «любой будущий текст».
4. Runtime привязывает текущую сессию к попытке либо запускает выбранного агента, если пользователь начал с кнопки карточки. Coordinator Run и дополнительные рабочие копии нужны только при согласованном делегировании/изоляции, не каждой простой задаче. От пользователя не требуются terminal handle, Run ID и внутренний placement JSON. Второй запрос не создаёт вторую попытку.
5. Текущий агент выполняет задачу сам; при необходимости согласованного параллельного выполнения координатор ведёт зависимости, а исполнители — связанные части. Карточка показывает этап, хост, активных агентов, блокер, последнюю запись и допустимые действия управления. Репозитории и ветки — детали исполнения, а не отдельные карточки вместо бизнес-задачи.
6. Перед передачей следующему исполнителю формируется короткий packet: актуальная задача/revision, цель подзадачи, допустимые репозитории/пути, входные SHA, решения и критерий приёмки. Системные события записывает runtime; содержательные решения/проверки — агент в notes/report/checkpoint. Не писать тысячи одинаковых строк в task.md.
7. После отчёта исполнителя запускается отдельный reviewer: другой attempt/agent, зафиксированные base/head SHA, критерии плана, результаты проверок и diff. Его текст — вывод модели, не автоматически подтверждённый CI. Замечания возвращаются исполнителю, затем ревью повторяется по новым SHA.
8. Для нескольких репозиториев отдельный integration этап проверяет согласованный набор изменений: API-контракт, версии, pipeline и интеграционные тесты. Один удачный unit test или MR одного репозитория не делает всю карточку готовой.
9. В карточке показывается результат: изменённые репозитории и SHA, реально выполненные проверки, вывод reviewer, оставшиеся ограничения, документы, ссылки MR. Пользователь принимает результат или возвращает замечания. Merge/deploy/запись в Kaiten требуют отдельной политики и разрешений; одобрение плана их не подразумевает.
10. Архив сохраняет историю, документы и ссылки. Автоматически не удаляет чаты/worktrees. Удаление слитых копий — отдельное recoverable действие после проверки чистоты, merge state и отсутствия активных агентов.

Кнопка в карточке должна показывать следующее допустимое действие: **Составить план → Одобрить и выполнить → Открыть выполнение → Проверить результат → Принять / Вернуть**. Не показывать одновременно десяток внутренних RPC-команд.

## Что должна гарантировать программа, а не обещание в prompt

- Владелец выполнения — runtime хоста, не открытое окно Mac. Закрытие UI не отменяет уже принятый запуск. Перезапуск VM требует отдельно настроенного штатного сервиса; нынешний учебный стенд такой гарантии ещё не даёт.
- Каждая стадия связана с task ID, revision, execution host, session и attempt; delegated execution дополнительно использует существующие Run/Dispatch. Отчёт без необходимых связей не переводит следующую стадию. Команда повторяется с idempotency key, события — с receipt/cursor. Хранение расширяется в существующей orchestration DB, не второй очереди в Markdown.
- Новый этап запускается по подтверждённому событию и проверенным prerequisites, а не по разбору фразы «готово» на экране терминала. Отчёт не равен приёмке; idle/exit/native child hook не равны завершению бизнес-задачи.
- Потеря связи означает **unverifiable**. Нельзя запускать замену исполнителю, пока не выяснен исход прежнего Dispatch. Используется существующий lifecycle/status store; новый status store для карточек не нужен.
- Перед передачей/завершением стадии проверяется наличие обязательного checkpoint/report и его соответствие revision/SHA. Если агент забыл документ, runtime запрашивает исправление или останавливается с понятным блокером. Он не придумывает журнал задним числом.
- Изменённый план не наследует старое approval. Продолжение другой revision возвращает gate пользователю. Проверки и ревью устаревают после изменения соответствующего head SHA.
- Смена аккаунта — новый provider launch с сохранённым task packet и проверкой прежней попытки, а не копирование access tokens/transcript. Не обещать перенос CLI-сессии между провайдерами, если это не поддерживает их адаптер.
- Дефолты agent/model/effort берутся из настроек пользователя. Профили planner/code/review могут их переопределять; недоступная модель даёт понятную ошибку. Параллелизм регулируется бюджетом/зависимостями, не произвольным глобальным «один worker». Бездействующий координатор ждёт события, не держит дорогой polling LLM-цикл.
- Instructions/MCP выдаются по роли и задаче; сторонние документы считаются данными. Строгий запрет координатору писать код требует capability/tool policy в launch adapter, а не строки в AGENTS.md. Такой enforcement нельзя обещать до отдельной проверки адаптеров.
- Kaiten получает одну понятную командную карточку/результат на значимую задачу, не каждую внутреннюю подзадачу. GitLab MR и CI привязываются к конкретному repository/head; статус «проверено» требует проверки именно этого head. Провайдеры подключаются через уже имеющиеся интеграции и их approvals.

## Этапы реализации после одобрения

### A. Один полный проход из обычного чата и карточки

- Сначала исправить выявленные bundled CLI/profile и prerelease-only update дефекты отдельными регрессионными тестами; не маскировать ошибки и не менять глобальную Orca.
- Реализовать host-owned получение/продолжение задачи существующей сессией: current project, точный task ID/revision, session identity, одно активное владение, идемпотентность. Не требовать обязательного coordinator/нового worker. Проверить capabilities старых peers; не создавать локальный fallback вместо сервера.
- Связать planner-диалог и кнопку исполнения с тем же механизмом карточки/attempt. Автоматически прикладывать ограниченный task packet при запуске/продолжении; проверить обнаружение интеграции обычным агентом в PTY, а не только прямым внешним вызовом CLI.
- Заменить техническую форму в основном UI на выбор профиля агента и **Одобрить и выполнить**. Диагностику Run/Dispatch оставить в details.
- Реализовать обязательный checkpoint/report gate и видимый блокер при его нарушении.
- Сначала один проект и одна карточка; обязательного выбора repository для задачи нет. Не внедрять массовый scheduler одновременно с этим срезом. Существующий delegated worker path сохранить, не создавать второй параллельный lifecycle.

Приёмка: обычный чат→выбор карточки→план/approval→та же сессия выполняет→видимый report→ручное решение на Mac и учебном SSH host; отдельно кнопка карточки проходит тот же lifecycle. Два конкурирующих чата, повторный запрос, изменение approved plan, закрытие UI и перезапуск runtime не порождают дублей и не теряют связь с попыткой. Сбой CLI, потеря связи и отсутствие report не дают ложный Done. Повторное продолжение использует checkpoint; входной контекст не растёт с числом посторонних задач. Для harness используется детерминированный протокольный агент; настоящая модель проверяется отдельно с согласованным аккаунтом/бюджетом.

### B. Независимое ревью и возврат замечаний

- Добавить тип стадии и доказательства SHA в существующие attempts/events с additive migration.
- По валидному implementation report запускать reviewer; его identity отделена от implementer.
- Ввести цикл findings→исправление→повторное ревью без повторного пересказа задачи пользователем. Условия остановки: лимит согласованных затрат/попыток, недостающая authority, неустранимый блокер — показать пользователю, не крутиться бесконечно.
- На карточке различать «агент считает готовым», «проверки выполнены» и «пользователь принял».

Приёмка: reviewer отвергает первую попытку, следующая исправляет замечание, изменение head делает прежнее ревью устаревшим, чужая revision/report не проходит gate. Отсутствующий report не запускает reviewer.

### C. Несколько репозиториев и итоговая интеграция

- Несколько подзадач/исполнителей работают в независимых копиях со стабильными repo/base/head ссылками.
- Integration attempt получает набор результатов, готовит согласованную проверку и MR-предложение. Не «сливать пять веток» без учёта разных Git-репозиториев.
- Сохранить независимое одобрение внешних записей и merge/deploy. Ветка координатора не обязана быть общей целью всех изменений.
- Отдельно предложить cleanup принятых рабочих копий с recoverable snapshot и проверкой реального состояния Git/процессов.

Приёмка: frontend+backend изменение с двумя MR, интеграционная ошибка на первой сборке, исправление, точные новые SHA и CI, возврат к карточке из нового чата/аккаунта по checkpoint. Никакого production deploy в QA.

### D. Несколько проектов и фоновые очереди

- Только после A–C добавить event-driven очередь разрешённых карточек и ограничения ресурсов/приоритеты; использовать существующие автоматики/Run lifecycle, не cron, который каждый раз шлёт всю историю всем агентам.
- UI даёт обзор пяти проектов: что выполняется, ждёт ревью/решения, где потерян контакт; переход открывает конкретную карточку и её агента.
- Секреты, аккаунты, глобальные полномочия, native-child наблюдения не наследуются молча от другого проекта.

Приёмка: пять синтетических проектов с несколькими одновременно работающими PTY, отключение/возврат клиента, перезапуск runtime, duplicate events, один offline host, смена аккаунта на завершённой попытке. Проверять отсутствие дублей, контекстных утечек и ложного done, а не число созданных коммитов.

## Рекомендуемая ближайшая граница

Сначала подтвердить уточнённый **этап A**: исправление CLI/update дефектов и один вертикальный срез, начинающийся обычным чатом. Это заменяет прежний обязательный coordinator-first план, а не добавляет ещё один режим. B–D — направление развития, не обещание включить всё одним большим патчем. Для первого настоящего model-driven прохода отдельно согласовать провайдера/модель, доступы, тестовый проект и бюджет; до этого никаких реальных токенов/корпоративного кода в учебном профиле.
