# Проверка beta: обычный чат → карточка → Review

Проводить на отдельной Opka beta и синтетическом проекте. Рабочая Orca, её профиль и старый сервер не участвуют. Наличие checklist не означает, что перечисленные действия уже проверены; фактические результаты — в журнале итерации 6.

## Установка и интеграция

1. Сверить версию, source commit и SHA256SUMS выпуска. Сохранить предыдущий установщик. Для обновления сохранить приватную резервную копию закрытого профиля Opka; не публиковать её.
2. Заменить только Opka.app после её закрытия. Не Orca.app. Подписи Developer ID/notarization нет; Gatekeeper не отключать.
3. В Settings проверить версию и CLI. Встроенный терминал должен использовать собственный ORCA_CLI_COMMAND/ORCA_USER_DATA_PATH, а не глобальную orca. Account login проверяется отдельно, секреты в отчёт не копировать.
4. В Tasks создать тестовый проект/файлы задач. В уже настроенном проекте: More actions → Enable agent task workflow. Существующие custom skills/AGENTS.md не должны переписываться. Затем открыть новый чат.

## Одна задача

1. Создать карточку с небольшой проверяемой ошибкой, целью и тестами. Утвердить текущий план.
2. В обычном чате проекта сказать «Выполни карточку …», не используя Work on task. При неоднозначности агент должен уточнить выбор.
3. Проверить переход в In progress и одну попытку текущего чата. Повторный claim не создаёт дубль. Второй чат не перехватывает владение.
4. Проверить checkpoint и activity после содержательного этапа; отчёт не должен оказаться в случайном каталоге. При ошибке выполнения агент сохраняет blocker, а не выдаёт готовность.
5. После фактических тестов ожидается Review, не Done. Открыть Reports & notes: отчёт/путь/результаты видны. Сверить изменения и самостоятельно выполнить тесты.
6. Перезапустить только тестовую Opka. Карточка, попытка, checkpoint и отчёт сохраняются. Продолжение другой сессией требует явного release владельцем, а не редактирования БД.
7. Принять проверенный результат либо вернуть на доработку. Только приёмка переводит в Done. Изменённый план требует нового approval.

## Обновления и ограничения

- Если новых версий нет, проверка обновлений не должна показывать ошибку лишь из-за prerelease-only канала. Сетевая ошибка не считается отсутствием обновлений.
- При новом выпуске: Download installer → проверка checksum → Open installer → ручная замена после закрытия Opka. Открытие DMG не должно завершать приложение само.
- SSH-проверку выполнять отдельно только на новом тестовом сервере. Старый host без новых методов должен вернуть понятный отказ совместимости, не локальный fallback.
- Любые реальные модельные тесты требуют согласованного расхода. Протокольный тест не заменяет поведение настоящего Codex/Claude. Автоматического независимого ревью и Engram пока нет.

Для замечания достаточно: действие, ожидаемый результат, фактический результат, версия и обезличенный screenshot. Не прикладывать auth/config/profile DB и корпоративные исходники.
