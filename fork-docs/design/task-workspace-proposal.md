# Предложение: проектные задачи поверх существующей Orca

Статус: технический план для согласования, не реализованная возможность. Основание — аудит исходников v1.4.235 и пользовательский сценарий. Проверки существующих контрактов приведены в [текущем журнале](../iterations/004-publication-and-ci.md).

## 1. Рекомендуемое решение

Добавить в Orca **проектные задачи с файловыми планами**, связав их с уже существующими Run/Task/Dispatch. Не ставить второй агентный движок, отдельную БД, новый постоянно работающий сервис или обязательный MCP.

Человек и агент читают один текст задачи. Интерфейс собирает список/дерево/доску из зарегистрированных файлов и достоверных runtime-фактов. Программа записывает факты выполнения; модель пишет смысловую часть: план, решения, выводы и следующий шаг. Не заставляем модель поддерживать вручную три одинаковых статуса в тексте, UI и БД.

Важное уточнение: «файлы вместо контекста чата» не означает «файлы вместо всей runtime БД». Файлы — источник текста и согласованного замысла; существующая runtime БД — источник фактов выполнения и приёмки. Экспорт текущего состояния в Markdown — читаемое представление, не вторая независимо редактируемая база.

## 3. Где документы живут

По умолчанию один каталог в общей папке multi-repo проекта. Пример **предлагаемого**, пока не существующего формата:

```text
project-root/
  .orca/project.yaml                # ID проекта и зарегистрированные источники
  docs/work/
    plan.md                         # цели/порядок больших задач, ссылки по ID
    tasks/
      pipeline-recovery/
        task.md                     # описание, план, критерии, зависимости
        notes.md                    # решения/выводы/смысловой журнал
        checkpoint.md               # краткий следующий шаг от владельца задачи
        reports/                    # отдельный отчёт каждой попытки/review
        activity.md                 # генерируемая runtime-хронология, read-only
  backend/
  windows-worker/
  frontend/
```

Для небольшой задачи достаточно task.md: остальные документы создаются по необходимости. Не требовать шести пустых файлов для исправления одной строки. История выполнения остаётся доступна через CLI/UI независимо от materialized activity.md.

Каталог настраиваемый: можно указать уже существующий docs/work либо другой путь пользователя. .orca/project.yaml хранит относительные пути и стабильные ID, не секреты и не абсолютные SSH credentials. Конфигурация не создаётся от простого открытия папки без подтверждения подключения задач.

Поддержать несколько источников: общий docs/work/tasks плюс выбранные каталоги backend/docs/tasks, frontend/docs/tasks и т. п. Общий экран агрегирует их и показывает repo/source. Источник владеет своим документом; другой проект может подключить его read-only либо ссылкой, но не заводит вторую независимо выполняемую копию.

Никакого «прочитать все .md и догадаться, где задача» на каждом старте. При подключении — ограниченное обнаружение conventional task roots и предложение их зарегистрировать. Затем watch только зарегистрированных каталогов на owning host. Весь проект показывается агрегированием индекса задач, а не семантическим перечитыванием документации.

Произвольную историческую документацию можно открыть как ссылку. Преобразование её в задачи — отдельное предпросмотренное действие с выбранным агентом; ничего не делим на тысячи карточек автоматически. Старые пользовательские планы не переписываем миграцией.

## 4. Разметка без собственного языка программирования

Обычный Markdown с небольшим YAML frontmatter. Использовать уже установленные yaml/remark primitives; не исполнять MDX, скрипты, шаблонные shell commands или HTML из документа.

```markdown
---
schema: 1
id: task-<stable-uuid>
title: Восстановить pipeline backend
kind: implementation
parent: null
depends_on: []
repos: [backend]
---
# Цель
Вернуть воспроизводимую сборку после восстановления доступа.

## Границы
Не изменять production-конфигурацию и Windows worker без согласования.

## Критерии приёмки
- [ ] Проверка проходит на согласованном commit SHA.
- [ ] Обновлена связанная инструкция сборки.

## План
- [ ] Собрать диагностику и предложить исправление.
- [ ] Реализовать в отдельной рабочей копии.
- [ ] Независимо проверить изменение и актуализировать документацию.

## Связанные документы
Ссылки на архитектуру, MR и checkpoint.
```

UUID не зависит от имени файла, Git branch, аккаунта или terminal handle. Repo aliases разрешаются через проектную конфигурацию в реальные Orca identities. Parent и deps — ссылки по ID; циклы, дубли и пропавшие ссылки дают явную ошибку, а не молчаливую догадку. Межрепозиторные зависимости в одном project workspace допустимы; связи между независимыми project workspaces сначала только ссылки.

Checkbox в плане — отметка автора о ходе работы, не доказательство прохождения тестов или merge. Для каждого пункта приёмки можно назначить стабильный ID и связать evidence с ним; непонятные секции Markdown остаются текстом и не теряются при round-trip. Статус выполнения не помещаем в свободно редактируемый frontmatter как второй источник истины.

Крупные подзадачи — отдельные файлы; мелкие действия — checklist. Никакого требования создавать worker на каждый checkbox. Общий plan.md содержит ссылки и порядок, а не копии описаний всех задач.

## 5. Кто владеет состоянием

| Данные | Единственный владелец записи | Как видят агент/UI |
| --- | --- | --- |
| Текст задачи, deps, план, заметки | Файл на host проекта; ревизия = content hash | Markdown editor и те же файлы/CLI |
| Утверждение плана | Квитанция в существующей runtime БД, привязанная к task ID + hash | Badge и resume summary; редактирование меняет revision |
| Запуски/dispatch/живость | Уже существующий execution-host lifecycle и status store | Fleet/agent list; потеря связи = unverifiable |
| Проектный этап/приёмка | Транзакционная надстройка в той же БД, ссылки на документы и попытки | Доска/CLI; экспорт activity.md — только представление |
| Семантический checkpoint | Файл владельца конкретной задачи | Краткая сводка со временем и отметкой актуальности |

Проектная задача переживает несколько Run и аккаунтов. Runtime Task означает выполнение конкретного пакета работ, а Dispatch — конкретную попытку. Нужна явная additive binding: project ID/task ID/document revision ↔ Run/task/dispatch/worktree/host, без смены смысла существующей TaskRow.

Новый проектный этап не зеркалирует TaskStatus: например, runtime completed означает «worker закончил», а проект может ждать review. В БД храним только недостающие связи и бизнес-события/приёмку, не дублируем provider status и process facts. Таблицы/миграции проектируем после фиксации контракта на этапе 3A.

Файлы легко копируются и читаются без Orca. Однако перенос только docs не восстанавливает достоверно живые процессы, approvals и dispatch authority. Для полного восстановления нужны documents + согласованный runtime backup/export. При потере БД импорт файлов восстанавливает намерения; все прежние выполнения помечаются неподтверждёнными, автоматический повтор выключен. Не обещаем прозрачную миграцию чата между аккаунтами: продолжается задача из checkpoint, а не обязательно тот же transcript.

## 6. Конкурентность и согласованность

- Единственный writer для переходов/назначений — runtime owning host. UI и CLI вызывают один contract; workers не меняют общий plan.md параллельно. У каждого worker отдельный report, координатор принимает результаты и обновляет общий план.
- При сохранении документа через приложение: expected content hash, проверка schema, временный файл в том же каталоге + rename, без молчаливого last-writer-wins. При конфликте показать обе версии и потребовать повторного чтения.
- Raw Edit из стороннего редактора разрешён как изменение текста, но не является approval/claim. Watch перечитывает файл, проверяет hash и показывает invalid/stale. Нельзя гарантировать отсутствие lost update между двумя произвольными внешними shell-writers; для managed agents используем revision-aware API и раздельные reports.
- Утверждённая ревизия плана хранится неизменно для попытки. Изменение файла во время работы отмечает plan changed; действующий worker не получает незаметно новый scope. Дальше явное решение: продолжить старую ревизию, остановить или перепланировать.
- Claim и старт проверяют approved revision, business deps, активную попытку и разрешения в транзакционной границе. Срок ожидания/lease не доказывает смерть worker: при unverifiable второй старт запрещён до reconciliation/явного recovery.
- Файловая запись и DB transaction не атомарны вместе. Не изображаем общую транзакцию: план сначала атомарно сохраняется, approval ссылается на точный hash; runtime transition и export receipt/outbox пишутся вместе, Markdown export повторяется идемпотентно после crash.
- Дедупликация событий по immutable ID, не по timestamp. Export cursor хранит подтверждённый диапазон. Повторный worker_done/reconnect не создаёт новый accepted result. Потерянный промежуточный export восстанавливается из БД.
- Решения и автоматические события различаются по actor/source. Текст отчёта — утверждение worker, не verified evidence. Approvals нельзя импортировать из отредактированного activity.md или из чужого Markdown.

## 7. Что автоматически, а что требует агента

Использовать внутренние lifecycle transitions и существующие hooks; не вешать отдельный shell hook на каждый файл/команду. Обязательные события относятся к own host, их запись не зависит от открытого desktop UI. Не писать транскрипт каждого токена в task journal.

| Событие | Автоматическое действие | Чего оно не доказывает |
| --- | --- | --- |
| Задача назначена/попытка создана | Связать IDs/revision, добавить timeline entry | Код ещё не изменён |
| Worker стартовал, ждёт вопрос/approval | Обновить runtime badge и очередь внимания | Весь проект не обязан переходить в blocked |
| Принят worker_done | Сохранить отчёт и перевести к проверке результата | Не считать проектную задачу done или merged |
| Процесс завершился без отчёта | finished_unverified/attention с ссылкой на transcript | Не повторять задачу автоматически |
| SSH недоступен | unverifiable с причиной и последним наблюдением | Не объявлять exited и не запускать дубль |
| Review/CI завершились | Сохранить evidence с SHA/ревизией и результатом | Старый зелёный pipeline не подтверждает новый SHA |
| Замечания review | Вернуть задачу исполнителю новой попыткой, сохранив историю | Не заставлять координатора тайно писать исправление |
| Merge подтверждён provider | Отметить конкретный repo/MR/commit | Это не атомарный merge остальных репозиториев и не deployment |

Содержание решений и корректность документации программа не угадает: это отдельные пункты задачи и работа агента/reviewer. Хуки могут потребовать checkpoint/report на границе, но не сочинять его за модель. Native subagent, где lifecycle ограничен, помечается как наблюдаемый child; нельзя обещать для него independent stop/claim/worktree без capability.

## 8. Рабочий цикл и границы ролей

Предлагаемые видимые этапы: Черновик → Готова → В работе → Проверка → Интеграция → Готово. Для исследовательской задачи интеграция может быть неприменима. Pause/blocker — отдельная причина, а не потеря истории. Archive скрывает выполненную задачу, не удаляя документы, chats или Git worktrees.

1. Пользователь даёт большую задачу; координатор или отдельный analyst уточняет требования, связанные документы и технические зоны. Создаёт project task и обоснованную декомпозицию.
2. Человек утверждает план, либо действует заранее заданная явная политика. Approved revision обязательна для managed start. Изменение плана не автоматически утверждается моделью.
3. Ready queue отдаёт подходящую задачу исполнителю через существующий worker-start/dispatch; одинаковую задачу нельзя незаметно взять дважды. В третьей итерации старт явный; автономный pull/scheduler — четвёртая.
4. Исполнитель получает только свой scope, ссылки, критерии, минимальные инструменты. Работает в своих Git worktrees, выдаёт report. Модель/провайдер/effort задаются конфигурацией запуска, не жёстко зашитым ID.
5. Independent reviewer оценивает конкретный diff/revision. Замечания направляются исполнителю, а не превращают координатора в незаметного coder.
6. Integration task объединяет принятые изменения, проверяет связку компонентов и docs. Набор поставки содержит отдельные base/head/MR/CI для каждого repo; общего атомарного Git merge между backend/frontend нет.
7. После выполненных критериев и нужных approvals фиксируется результат. MR, deployment и чистка рабочих копий — разные действия; автоматически удалять branch или production deploy только из-за done нельзя.

Не обещаем, что промпт «ты только координатор» технически запретит ему Edit или shell. Enforcement write scope и роли через реально ограниченный tool gateway — отдельный этап 4. Третья итерация делает передачу/результаты наблюдаемыми, но не объявляет prompt надёжным sandbox.

Глобальный координатор нескольких проектов получает короткие сводки и ссылки, а не все планы/логи в контекст. Каждый проектный coordinator отвечает за свою задачу; pending user decision виден в общей очереди. Resource-aware concurrency проектируется отдельно; нет произвольного лимита одного worker и обещания неограниченного параллелизма на 12 ГБ RAM.

## 9. Интерфейс и агентный доступ

Сохраняем incumbent Orca, её sidebar, editor, tokens и keyboard conventions. Это план поведения, не новый визуальный макет.

- В контексте общей папки: раздел «Задачи проекта» с обзором по всем подключённым источникам. В контексте repo — фильтр по этому repo; multi-repo задача остаётся одной карточкой.
- Список/дерево по умолчанию, доска — альтернативный вид тех же данных. Поля: этап, приоритет, зависимости/блокер, repos, исполнитель, хост, следующая необходимая операция. Фильтры «нужно моё решение», «готово к взятию», «активные».
- Детали задачи: цель/критерии/план; вкладки или секции «Журнал», «Попытки и агенты», «Изменения и проверки». Доступны исходный Markdown и обычный preview. Открытие одиночного task.md даёт ту же задачу по ID, а не второй импорт.
- Рядом с активной задачей — число workers и pending approvals; подробности по клику из существующего agent registry/fleet. Не открываем терминал каждого worker ради счётчика.
- Действия: создать, редактировать/rename, утвердить план, начать/продолжить, остановить попытку с подтверждением, запросить review, архивировать/восстановить. Delete — отдельное явное действие с проверкой активных попыток; не удаляет repo/чат. Drag-and-drop разрешён только для допустимого перехода, не обходит approval/CI gates.
- Пусто: выбрать/создать каталог задач. Invalid document: путь и ошибка, исходник доступен, запуск запрещён. Offline: последний снимок с временем/host, read-only для host-owned операций. Conflict: выбор версий вместо перезаписи.
- На телефоне — тот же API/контракт, компактный список и последовательные детали, очередь approvals. Не строим новый мобильный relay; проверяем существующий transport отдельно.

Один небольшой namespace в существующем CLI, например `orca project-task list/show/context/create/update/start/report`. Это предлагаемые команды, **сейчас их нет**. `context` выдаёт bounded Markdown/JSON: цель, approved revision, scope/запреты, принятые результаты, текущие attempts, блокеры и следующий шаг. Подробный timeline — по запросу с cursor.

Для агента достаточно короткой проектной инструкции с task ID и командой context; scoped skill помогает работе с задачами, но не является единственной защитой. Контекст подмешивается при attach/resume и изменении revision, не целиком на каждый tool call. При недоступности runtime файлы читаются напрямую, но автоматический старт/изменение runtime state недоступны.

## 10. Нагрузка, хранение, безопасность

- Один индекс метаданных на host, восстановимый из зарегистрированных файлов. Не новый процесс на задачу, не polling всего диска, не embeddings/LLM для индексации.
- Debounced watch, bounded queue, pagination, lazy body/journal. Reconnect ловит пропуски через ограниченную сверку registered roots; overflow явно показывает incomplete index, а не тихо теряет задачи.
- Тестовые наборы: 1 000 задач/10 000 событий, вложенные источники, массовый rename и большой журнал. Измерить baseline RSS/CPU и накладные расходы; пределы capacity и пороги регрессии утвердить по измерению, не обещать произвольные миллисекунды заранее.
- Idle UI не вызывает повторный parse; изменение одного документа инвалидирует затронутый срез индекса. Закрытие вкладки снимает UI subscriptions, но не останавливает host-owned workers.
- Архив читается по запросу; retention не удаляет пользовательские документы и не рвёт audit links. Для общего non-Git root можно отдельно подключить Git только для документации, но не создавать/пушить новый repo без разрешения.
- Документы задач не содержат секретов. В links/evidence сохраняем пути и безопасные summaries, не stdout с токенами. Ни Markdown, ни импортированные требования не выдают полномочия. Security prompts используют существующую защищённую поверхность Orca.
- Realpath/host fencing, запрет symlink/path traversal, безопасный YAML без executable tags, versioned schema, read-only unknown future versions, cross-platform paths, ограничения размера и числа roots обязательны до первой managed write.
- Kaiten: одна командная карточка на понятный deliverable, внутренние шаги остаются в проекте. Пока сохраняем links и готовим summary. Автоматическая запись/двусторонний sync, экспорт корпоративных требований и новый MCP не входят в третью итерацию.

## 11. Сравнение альтернатив

Проверено 21 октября 2026, по первичным источникам. Это выбор подхода, не аудит безопасности сторонних пакетов.

- [planning-with-files](https://github.com/OthmanAdi/planning-with-files), [quickstart](https://github.com/OthmanAdi/planning-with-files/blob/master/docs/quickstart.md): берём разделение плана/выводов/журнала, изоляцию независимых тем и короткий handoff. У него есть lifecycle adapters; не предполагаем одинаковые capabilities всех CLI и не устанавливаем их вслепую. Сам по себе skill не заменяет runtime claim, review и project UI.
- [Beads](https://github.com/gastownhall/beads): полезные принципы stable IDs, ready queue и atomic claim. Текущая документация указывает Dolt, а не простую Markdown-only систему; подключение добавило бы ещё один lifecycle/storage рядом с Orca. Не включать как обязательную зависимость.
- [Temporal](https://docs.temporal.io/workflows): полезен принцип сохранения событий и восстановления workflow. Полный Temporal для этого форка пока не оправдан: существующий Orca runtime уже выполняет значительную часть нужной работы. Не обещаем exactly-once внешнего эффекта только потому, что есть журнал.

Рекомендация — собственный тонкий project-document слой и adapter к существующему runtime. Исходники внешних проектов не копировались, зависимости не устанавливались; лицензии потребуется проверить отдельно, если решим переносить код.
